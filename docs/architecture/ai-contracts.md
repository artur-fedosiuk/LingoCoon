# AI Learning Contracts

## Status

Approved AI contract baseline. The first-mission contract below is recommended for implementation approval.

- Version: 1.1
- Last reviewed: 2026-08-30

## Contract rule

AI is a bounded component inside the learning system. It does not own authorization, persistence, billing, or unvalidated learner state.

## Request context

An AI learning request may include:

- authenticated learner context;
- target and native language;
- current goal and activity type;
- relevant learner profile slice;
- recent evidence needed for the decision;
- allowed difficulty and duration;
- output purpose and completion criteria.

Send the minimum context required for the task. Do not send unrelated personal data.

## Required output categories

Depending on the operation, the model may return:

- an activity definition;
- a learner-facing response;
- an evaluation;
- structured learning signals;
- a recommendation;
- a fallback decision.

Every output must be schema-validated, bounded in size, associated with a request identifier, and safe to reject.

## Evaluation requirements

An evaluation should separate:

- observed learner input;
- expected task outcome;
- detected issue;
- confidence;
- explanation;
- priority;
- suggested retry.

Do not present low-confidence inference as a definitive correction.

## Prompt and abuse controls

- Treat learner content as untrusted input, not as system instructions.
- Keep system behavior and persistence rules outside learner-controlled text.
- Bound conversation history, output size, and activity duration.
- Apply authentication, authorization, rate limits, and usage budgets server-side.
- Log operational metadata without logging unnecessary personal content.
- Provide provider-independent fallback behavior.

## Quality evaluation

Before production use, evaluate representative cases for:

- level appropriateness;
- factual and linguistic accuracy;
- useful correction selection;
- acceptable language variants;
- accent and hesitation tolerance;
- prompt injection resistance;
- latency and provider failure;
- cost per completed session.

## First-mission evaluation workflow

```text
validate request
  → authorize learner and session
  → reserve per-user and global usage
  → build server-owned system instructions
  → call bounded evaluator
  → validate and normalize output
  → persist event and at most one priority signal
  → commit usage
  → derive recommendation with application logic
```

Any failure after reservation releases or reconciles the reservation. Retries require an explicit retry policy and consume the same operation budget.

## Evaluation request contract

```ts
interface MissionEvaluationRequestV1 {
  contractVersion: 1;
  requestId: string; // UUID generated by the server
  sessionId: string;
  activity: 'writing' | 'speaking';
  targetLanguage: string;
  feedbackLanguage: string;
  cefrLevel: 'A1' | 'A2' | 'B1' | 'B2' | 'C1' | 'C2';
  taskKey: 'workplace-self-introduction-v1';
  learnerResponse: string;
  responseSource: 'typed' | 'confirmed_transcript';
  targetConcepts: Array<{
    conceptKey: string;
    label: string;
  }>;
  previousAttempt: null | {
    response: string;
    priorityConceptKey: string | null;
  };
}
```

Validation limits:

- `learnerResponse`: 1–1,200 Unicode characters;
- `targetConcepts`: 0–5 entries, each key and label bounded to 80 characters;
- `previousAttempt.response`: at most 1,200 characters;
- languages and CEFR level come from allowlists;
- `taskKey` resolves to a server-owned activity definition;
- unknown keys and client-supplied system instructions are rejected.

The provider payload omits database identifiers and unrelated profile fields. If provider abuse controls need a stable user key, send a service-specific pseudonymous hash rather than the Supabase subject identifier.

## Evaluation result contract

```ts
interface MissionEvaluationResultV1 {
  contractVersion: 1;
  taskCompletion: {
    met: boolean;
    evidence: string;
  };
  comprehensibility: {
    level: 'unclear' | 'partly_clear' | 'clear';
    evidence: string;
  };
  targetLanguageUse: {
    usedConceptKeys: string[];
    missingConceptKeys: string[];
  };
  strength: string;
  priorityCorrection: null | {
    category: 'vocabulary' | 'grammar' | 'communication';
    conceptKey: string;
    observedExcerpt: string;
    suggestedForm: string;
    explanation: string;
  };
  retryInstruction: string;
  confidence: {
    score: number; // 0..1
    reason: string;
  };
}
```

Output limits:

- exactly one strength and zero or one priority correction;
- evidence, feedback, and explanation fields are each capped at 300 characters;
- concept keys must be a subset of the request or an approved concept registry;
- confidence is clamped to `0..1` and cannot be presented as definitive below the approved threshold;
- no HTML, Markdown links, external URLs, hidden instructions, profile mutations, scores, rewards, or recommendation status;
- schema-invalid output is rejected in full, never partially persisted.

## Speaking boundary

The first mission evaluates a learner-confirmed transcript for task completion, target-language use, grammar, vocabulary, and communication. A transcript alone must not produce a pronunciation or accent error signal.

Pronunciation scoring requires a separately approved audio-evaluation contract, representative accent testing, confidence calibration, privacy review, and a usable non-audio fallback. Raw audio is not persisted by default.

## Recommendation boundary

AI may propose a priority correction but does not choose the learner's next persistent state. Application logic creates a recommendation only from:

- the accepted evaluation result;
- deterministic session evidence;
- active learner goals and preferences;
- existing non-dismissed signals;
- configured pedagogical priority rules.

The learner can save, dismiss, edit, replace, or start the recommendation. These actions are stored as learner decisions, not model inference.

## Authorization and validation boundary

- The server derives `userId` from the authenticated session.
- The session must belong to that user and be active.
- The server owns system instructions, task definitions, output schema, model choice, persistence rules, and usage limits.
- Learner text is placed only in delimited user-content fields.
- AI output passes runtime schema validation and application invariants before any write.
- A duplicate `requestId` returns the existing accepted result or safe failure and does not call the provider twice.

## Abuse and zero-budget controls

Every provider call requires an atomic `UsageReservation` before dispatch:

```ts
interface UsageReservation {
  requestId: string;
  userId: string;
  operation: 'text_evaluation' | 'text_generation' | 'tts_characters' | 'stt_audio';
  requestedUnits: number;
  status: 'reserved' | 'committed' | 'released';
  expiresAt: string;
}
```

Controls must include:

- per-user burst and daily limits;
- a global daily hard stop below the verified free provider allowance;
- bounded concurrent requests;
- operation-specific units: estimated tokens, characters, or audio bytes/duration;
- retries charged to the original reservation;
- no automatic paid overage;
- minimal usage logs without prompts, transcripts, or audio.

Numeric caps are a blocking deployment decision because current free allowances and provider terms must be verified immediately before implementation. Until then, no provider-backed feature is considered zero-budget safe.

## Fallback behavior

| Failure | Required learner experience |
| --- | --- |
| AI unavailable, timeout, invalid output, or budget exhausted | Save the response only with consent, acknowledge completion, offer deterministic checklist feedback, and allow retry later. |
| STT unavailable | Keep recording local if possible, otherwise provide typed speaking-mode fallback; never imply pronunciation was evaluated. |
| TTS unavailable | Show the transcript, native audio controls when available, and a clear retry action. |
| Low evaluation confidence | Present the observation as a suggestion, do not create an active error signal automatically, and ask the learner to confirm or dismiss it. |
| Persistence failure | Keep the learner's response in current-session memory, explain that progress was not saved, and provide retry or copy options. |

## Quality and observability gates

- 100% schema-valid accepted outputs in tests; malformed responses always enter fallback.
- At least 90% reviewer agreement that the selected correction is useful on the approved evaluation set before release.
- Fewer than 2% high-confidence corrections judged incorrect on that set.
- No pronunciation finding derived from transcript-only input.
- Text-evaluation target: p95 under 10 seconds; speech-to-feedback target: p95 under 20 seconds, with explicit timeout fallback.
- Record request ID, operation, model/provider alias, latency, normalized usage units, outcome, retry count, and error category.
- Track completion rate, fallback rate, schema-rejection rate, learner correction acceptance, retry improvement, and daily global usage.

## Open implementation decisions

Before code or provider changes, approve:

1. current provider choices and verified free allowances;
2. numeric per-user and global budgets;
3. confirmed-transcript retention duration;
4. the representative evaluation set and reviewer process;
5. whether text-based speaking evaluation is sufficient for the first release or audio evaluation is required later.
